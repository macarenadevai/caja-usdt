## 1. Constitution (project principles)

1. **The WDK CLI is the core building block** — every wallet operation goes through `wdk` (subprocess). It's the literal prize 1 requirement: "Best project built with the WDK CLI (and/or its bundled MCP server)".
2. **Functionality > aesthetics** — the UI must look premium, but every pixel is justified by a demo function.
3. **Disciplined scope** — 3 views (Collect, Send, Agent) sharing ONE backbone: WDK wallet + payment detector. Nothing else gets in without justification.
4. **The agent is a luxury, not a dependency** — Collect and Send work 100% without the agent. If the LLM fails in the demo, the rest stays alive.
5. **Zero secrets in git** — seed, passphrase and API keys live in `.env` (gitignored).
6. **All code is written now** — hackathon rule: project code is committed after the official start (already started). template-evm is our own scaffold, allowed as a base.

## 2. Concept

A business (store, freelancer, remittance) that manages its **USD₮ cashbox** with a single app:

- **Collect** — POS terminal: enter the amount, a QR appears, the customer pays, the screen confirms live.
- **Send** — remittance/payment to a supplier or family with package-style tracking (*sent → confirmed → done*).
- **Agent** — you type "pay $10 to my supplier" in a chat and an AI agent (DeepSeek + wdk-mcp) prepares the operation; you confirm and it executes.

All on the business's non-custodial wallet, generated by the WDK CLI. Demo on Sepolia with mock USD₮ (Pimlico/Candide faucets) + a local payer wallet for the demo.

## 4. User Stories

### US-1 — Collect at the cashbox (P1)

The business owner collects from a customer with crypto without a bank terminal: enters the amount, shows a QR with the address and amount, and when the customer pays the screen confirms live.

**Why P1**: it's the first half of the demo and the most tangible use case (PayKit in miniature).

**Independent test**: creating an invoice and paying it with the local payer wallet, the status must move to *paid* with no manual intervention.

**Acceptance scenarios**:
1. **Given** a cashbox with a WDK wallet on Sepolia, **When** the owner enters an amount and creates the invoice, **Then** a QR with address + amount is generated and the invoice stays *pending*.
2. **Given** a *pending* invoice, **When** the payer wallet sends mock USD₮ to the address (outside the app), **Then** the detector (poll ≤5s) updates the invoice to *paid* and the UI shows it with visual confirmation.
3. **Given** a paid invoice, **When** the detail is opened, **Then** amount, address, tx hash (if available) and time are shown.

### US-2 — Send with tracking (P1)

The owner sends USD₮ to a supplier or family member and sees progress like a courier shipment.

**Why P1**: the second half of the demo — the "remittances with tracking" side.

**Independent test**: sending an amount from the cashbox to a second wallet, the status advances from *sent* to *confirmed* automatically.

**Acceptance scenarios**:
1. **Given** a funded cashbox, **When** the owner sends `{amount, address}` and confirms, **Then** the backend executes `wdk send` and the operation enters *sent* state with its tx hash.
2. **Given** a *sent* operation, **When** the tx reaches confirmation on Sepolia, **Then** the status changes to *confirmed* and the tracking shows the completed step.
3. **Given** an amount with insufficient balance, **When** a send is attempted, **Then** the UI blocks with a clear error ("insufficient balance") without calling the CLI.

### US-3 — Cashbox agent (P1)

The owner operates the cashbox in natural language: "how much do I have?", "pay $10 to 0x123..." — the agent translates to real wallet operations via wdk-mcp, proposes, the owner confirms, it executes.

**Why P1**: it's the prize 1 differentiator (agents with wallets via CLI/MCP) and almost nobody else will attempt it at this level.

**Independent test**: asking the chat for the balance, the agent replies with the wallet's real number; requesting a transfer generates a proposal that requires confirmation.

**Acceptance scenarios**:
1. **Given** the chat open, **When** the owner asks "how much USD₮ do I have?", **Then** the agent queries wdk-mcp and replies with the real balance (not invented).
2. **Given** the instruction "send $10 to 0x...", **When** the agent interprets it, **Then** it shows a proposal `{to, amount, token, network, fee}` and does NOT execute without confirmation.
3. **Given** a visible proposal, **When** the owner confirms it, **Then** `wdk send` executes and the result appears in the chat and the ledger.
4. **Given** an ambiguous instruction or no funds, **When** the agent processes it, **Then** it replies asking for clarification or reporting insufficient balance — it never fakes an execution.

### US-4 — Operations ledger (P2)

Every operation (collects and sends) stays in a history with status, time and amounts.

**Why P2**: reinforces the pitch ("your organized cashbox") but doesn't block the demo.

**Acceptance scenarios**:
1. **Given** N operations, **When** the ledger is opened, **Then** they are listed sorted by date with status and amount.
2. **Given** an operation, **When** filtered by status, **Then** only the matching ones appear.

### US-5 — Multi-network (P2)

Network selector to operate (Sepolia in the demo; ethereum, solana, tron, base real ones available via the CLI).

**Why P2**: WDK is multi-chain by design; showing it earns points, but the demo can live on Sepolia.

**Acceptance scenarios**:
1. **Given** the network selector, **When** the network is changed, **Then** balances and invoices use that network.
2. **Given** a network without registered USDT, **When** a collect is attempted, **Then** the UI warns and blocks the token.

### US-6 — Gasless with smart account (P2, if time allows)

Use the ERC-4337 smart account derived by WDK so the payer doesn't need ETH for gas (prize 2: $500).

**Why P2**: it's the complete prize 2, but requires bundler/paymaster config (time risk).

**Acceptance scenarios**:
1. **Given** a deployed smart account, **When** the customer pays without native ETH, **Then** the tx executes via paymaster.
2. **Given** missing gasless config, **When** it's used, **Then** the app reports it without breaking the rest.

## 5. Functional Requirements

- **FR-001**: Backend exposes a REST API on `localhost:8788` (CORS for the frontend).
- **FR-002**: Every wallet operation goes through the `wdk` CLI as a subprocess with `WDK_PASSPHRASE` from `.env` (never in visible argv).
- **FR-003**: Payment detector: 5s poll of `wdk get balance --network sepolia --token usdt` (and `--token eth` for gas); an invoice is marked *paid* when the address balance exceeds the expected amount.
- **FR-004**: Invoice model: `{id, amount, token, network, address, status: pending|paid|expired, createdAt, paidAt}`.
- **FR-005**: Transfer model: `{id, to, amount, token, network, status: pending|sent|confirmed|failed, txHash, createdAt, confirmedAt}`.
- **FR-006**: Agent: chat → DeepSeek (function calling) → wdk-mcp tools; any `send` requires a proposal + human confirmation.
- **FR-007**: Frontend: a single dashboard page with 3 tabs (Collect / Send / Agent) + ledger; 3s state polling.
- **FR-008**: Secrets (WDK_PASSPHRASE, DEEPSEEK_API_KEY) ONLY in `.env` (gitignored). `.env.example` with placeholders committed.
- **FR-009**: Clean frontend build (`npm run build`) and backend startable with `npm start`.
- **FR-010**: Repo README.md: what it is, how to run it, stack, demo video.

## 6. API Contracts

```
GET  /api/status                 → {wallet, defaultNetwork, networks[], tokens[]}
GET  /api/balance?network=&token → {network, token, formatted, usd}
GET  /api/address?network=       → {network, address}
POST /api/invoice {amount, token, network}
                                 → {id, amount, token, address, qrPayload, status}
GET  /api/invoice/:id            → {id, amount, token, status, paidAt}
POST /api/send {to, amount, token, network, confirm:true}
                                 → {id, status:'sent', txHash} | {error}
GET  /api/transactions           → [{type:'invoice'|'send', id, amount, status, createdAt}]
POST /api/agent/message {text}   → {reply, proposal?{id, to, amount, token, fee}, needsConfirmation}
POST /api/agent/confirm {proposalId}
                                 → {result, txHash?}
GET  /api/agent/proposals        → [proposal...]
```

Errors: `{error: string, code: string}` with HTTP 400/404/409/500.

## 7. Technical Decisions

| # | Decision | Options | Chosen | Reason |
|---|---|---|---|---|
| TD-1 | WDK integration | Direct Node SDK vs **CLI subprocess** | CLI subprocess | Prize 1 literal: "built with the WDK CLI as core building block". Same data, defensible before judges. |
| TD-2 | Persistence | SQLite vs JSON | state.json | Zero native deps, enough for the demo; simple lock read/write. |
| TD-3 | Frontend wallet | Keep Reown AppKit vs **remove** | Remove AppKit/Wagmi/x402 | The payer uses their own wallet (QR scan / local CLI wallet). Fewer deps = less build risk. viem stays only if the backend needs it (it doesn't: the CLI covers it). |
| TD-4 | Payment detector | Indexer/history vs **balance polling** | Polling `wdk get balance --token usdt` 5s | Official, no indexer API key (history requires an indexer key). 5s latency acceptable for the demo. |
| TD-5 | Demo payer | MetaMask + faucets vs **local WDK wallet** | Local `pagador` wallet (wdk wallet create) | Zero dependency on live extensions/faucets; same real mechanism (send → cashbox address). |
| TD-6 | Agent | Claude Desktop vs **custom MCP client + DeepSeek** | MCP client SDK (@modelcontextprotocol/sdk) + DeepSeek | DeepSeek supports function calling; wdk-mcp is an agnostic stdio server. Don't depend on Claude. |
| TD-7 | Agent security | Direct execution vs **human confirmation** | Proposal + confirmation | Honest and safe demo: the agent proposes, the human executes. Avoids "the AI invented a transfer". |
| TD-8 | Demo network | ethereum mainnet vs **sepolia** | Sepolia | Mock USD₮ with faucets (Pimlico/Candide), faucet gas. The CLI already has it with a registered token. |
| TD-9 | Daemon unlock | Manual vs **per command** | Wrapper re-unlock with WDK_PASSPHRASE per operation | The daemon has a TTL (~5 min); the wrapper guarantees unlock always. |
| TD-10 | Backend framework | Express vs Fastify vs Hono | Express 5 | Lightweight, known, stable ecosystem. |
| TD-11 | Node | 22.22.2 (server) vs install 24 | 22.22.2 | WDK requires 22.18+ ✓. Next 16 requires ≥20.9 ✓. If the Next build fails on Node 22, install Node 24 (contingency). |
